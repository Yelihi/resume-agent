# 이력서·포트폴리오 작성 및 검토 기본 규칙

상태: **설계 기준선**. 향후 이력서 작성·검토 skill 또는 agent가 기본으로 적용할 규칙이다. 이 문서 전체를 실행 시 읽거나 자동 주입하지 않는다. 현재 실행 규칙은 `backend/app/review/prompts.py`의 `BASE_PRINCIPLES`에 별도로 구현되어 있으며, 상세 규칙 전체의 반영을 의미하지 않는다.

## 1. 기본 목적

- 모든 경험을 설명하는 것이 아니라, 지원 직무에 맞는 핵심을 선택해 어필한다.
- 후보자의 실제 경험에서 기준, 판단, 선택 이유와 근거를 발견한다.
- 후보자가 설명하고 방어할 수 있는 주장만 사용한다.
- 각 핵심 주장은 근거와 연결하고, 후보자가 대비할 수 있는 면접 질문으로 이어지게 한다.
- 이력서는 핵심 메시지와 근거를 빠르게 읽히게 하고, 포트폴리오는 그 판단과 실행 과정을 더 깊게 증명한다.

## 2. 우선순위와 절대 규칙

다음 순서로 판단한다.

```text
안전·기밀
→ 사실성
→ 직무 관련성
→ 판단과 선택
→ 근거
→ 차별화
→ 가독성
→ 의도한 면접 질문
→ 표현 품질
```

다음은 예외 없이 지킨다.

- 회사의 기밀 코드, 데이터 또는 비공개 정보를 이력서와 포트폴리오에 넣지 않는다.
- 사실, 수치, 성과, 역할, 기술과 소유권을 만들거나 과장하지 않는다.
- 후보자가 설명할 수 없는 기술이나 주장을 싣지 않는다.
- 클론 코딩을 실제 문제 해결 경험처럼 포장하지 않는다.
- 동작하지 않는 프로젝트를 동작하는 결과물처럼 소개하지 않는다.
- 팀 프로젝트의 개인 기여를 부풀리지 않고, 한계와 미완성 상태를 숨기지 않는다.
- AI와 협업한 경우 후보자의 판단, AI의 역할, 검증 방법을 구분한다. 검증하지 않은 AI 결과를 후보자 자신의 판단처럼 표현하지 않는다.
- 공개 여부와 최종 표현은 사용자가 승인한다.

## 3. 공통 작성·검토 원칙

- 먼저 `무엇을 어필할 것인가`를 정하고, 그 메시지를 증명하지 못하는 내용은 줄이거나 제거한다.
- 기술명과 기능 수보다 문제, 제약, 선택 이유, 대안, 트레이드오프와 결과를 드러낸다.
- 개인의 기준과 신념을 추상적인 구호로 쓰지 않고 실제 결정의 근거로 보여준다.
- 독자가 후보자의 생각 흐름을 따라갈 수 있게 하되, 모든 경험을 같은 `문제 → 원인 → 해결` 틀에 억지로 맞추지 않는다.
- 신입은 학습 속도와 성장 가능성을, 경력자는 실무 수준의 판단력과 책임 범위를 중심으로 증명한다.
- 차별화는 과장된 표현이 아니라 희소한 문제, 실제 제약, 선택과 증거에서 만든다. 표현과 구성은 이를 잘 전달하도록 다듬는다.
- 주장마다 `이 주장을 뒷받침하는 근거는 무엇인가`, `면접에서 어떤 질문을 유도하는가`, `후보자가 답할 수 있는가`를 확인한다.
- 정보가 부족하면 내용을 만들지 않고, 정보 이득이 큰 질문부터 한 번에 하나씩 묻는다.

## 4. 사용자의 핵심 엔지니어링 관점

다음 관점을 기본 포지셔닝 후보로 사용한다.

> 설계의 기반은 사용자가 문제없이 직관적이고 편하게 사용할 수 있도록 하며, 백그라운드의 데이터·네트워크 처리가 효율적으로 진행되게 하는 것이다.

경험에 실제 근거가 있을 때 다음 판단을 찾아 어필한다.

- 사용자의 즉각적인 피드백과 낙관적 업데이트
- 백그라운드 검증, 실패 시 복구 또는 롤백
- 사용 목적을 돕는 적절한 애니메이션
- 데이터 양과 탐색 방식에 맞춘 페이지네이션
- API 호출 시점, 중복 호출, 취소, 캐싱과 무효화 전략
- 모바일 환경에서의 SPA 사용성과 인터페이스
- 데이터 정합성, 네트워크 효율, 오류 복구
- 테스트, 로그, 모니터링, 배포와 확장·변경 가능성

이 항목을 모든 프로젝트에 강제로 넣지는 않는다. 후보자가 실제로 판단하고 설명할 수 있는 항목만 선택한다.

## 5. 포트폴리오 기본 규칙

### 해야 할 것

- 여러 프로젝트를 얕게 나열하기보다 하나의 핵심 프로젝트에 집중한다.
- 프로젝트를 실제로 배포하고 꾸준히 업데이트한다.
- 프로젝트의 기준과 신념, 선택 이유와 포기한 대안을 보여준다.
- 기능 수보다 운영 가능한 제품의 관점에서 변경·확장, 테스트, 로그, 모니터링, 배포와 장애 대응을 보여준다.
- AI와 협업한 과정, 역할 분담, 검증과 수정 과정을 이력서·포트폴리오·블로그 중 적절한 위치에 남긴다.
- GitHub를 근거로 제시한다면 README와 의존성 관리 상태까지 관리한다.
- 프로젝트의 현재 동작 상태, 개인 기여, 팀의 역할과 한계를 솔직하게 밝힌다.

### 하지 말아야 할 것

- 이력서 내용을 길게 되풀이하는 포트폴리오를 만들지 않는다.
- 관리되지 않는 블로그나 단순 지식 정리만 있는 블로그를 근거로 내세우지 않는다.
- 의미 없는 일일 커밋 기록을 성실성의 근거처럼 제시하지 않는다.
- 오픈소스 문서 기여만으로 전체 개발 역량을 대표하지 않는다. 문서 작업 자체의 가치는 인정하되 다른 기여와 역할을 정확히 구분한다.
- 설명할 수 없는 기술, 직무와 관계없는 경험, 너무 많은 프로젝트를 넣지 않는다.
- 클론 코딩, 동작하지 않는 프로젝트, 기능 목록만으로 역량을 포장하지 않는다.
- 방치한 팀 프로젝트를 완성된 개인 성과처럼 소개하거나 한계를 숨기지 않는다.
- 읽는 피로도를 높이는 도식과 설명을 추가하지 않는다. 도식은 관계나 판단을 더 쉽게 이해하게 할 때만 사용한다.

## 6. 이력서 기본 규칙

### 해야 할 것

- 최근 경험과 가장 강조할 경험을 위에 둔다.
- 각 영역의 역할과 맥락을 짧게 설명해 검토자가 빠르게 이해하도록 돕는다.
- 자기소개는 약 3줄 안에서 핵심 포지셔닝을 제시하고, 본문은 그 주장의 근거가 되게 한다.
- 지원 회사와 직무에 따라 사실은 유지한 채 내용의 선택, 순서와 강조를 조정한다.
- 여러 채용 공고의 공통 요구사항을 분석하되, 실제 근거가 있는 요구사항만 연결한다.
- 이력서를 최소 6개월마다 점검하고 오래되거나 약한 이력은 정리한다.
- 외부 링크 이동을 최소화하고 핵심 근거를 이력서 안에 둔다. 링크는 실질적인 증거가 되는 한두 개를 우선한다.
- 약 3페이지 안에서 핵심을 선택하는 것을 기본으로 삼는다. 별도 포트폴리오는 이 분량에 포함하지 않는다.
- 기계적인 이력 나열보다 필요한 범위의 배경과 판단을 담아 이야기가 이어지게 한다.
- 후보자가 답할 수 있고 강점을 드러낼 면접 질문이 나오도록 표현을 설계한다.
- 간단한 프로필 사진을 기본 선택지로 고려하되, 지원 국가·회사 관행과 개인정보 노출 위험을 함께 확인한다.

### 하지 말아야 할 것

- 누구나 사용하는 템플릿에 내용을 억지로 맞추지 않는다.
- 이해에 필요한 맥락까지 지나치게 축약하거나, 반대로 핵심을 가릴 정도로 많이 넣지 않는다.
- 모든 항목을 같은 서술 패턴으로 작성하지 않는다.
- 과대 포장하거나 오래되고 중요하지 않은 이력을 그대로 쌓아두지 않는다.
- 기술 스택을 고민 없이 나열하거나 `상·중·하`처럼 근거 없는 숙련도 등급을 쓰지 않는다.
- 희망 연봉을 쓰지 않는다.
- 관리되지 않는 GitHub와 블로그를 링크하지 않는다.
- 자기소개나 경력 기술을 이력서 안에서 지나치게 길게 작성하지 않는다.
- 집중을 방해하는 다단 그리드와 복잡한 배열, 과도한 디자인을 사용하지 않는다.

## 7. 기본 질문 축

작성·검토 과정에서는 다음 중 현재 결과를 가장 크게 바꿀 질문을 하나씩 선택한다.

- 이번 지원에서 가장 어필하려는 역량은 무엇인가?
- 해당 결과에서 후보자가 직접 소유하고 결정한 부분은 무엇인가?
- 어떤 사용자 문제를 왜 중요하다고 판단했는가?
- 검토한 대안과 선택하지 않은 이유는 무엇인가?
- 시간, 인력, 기술, 운영상의 제약은 무엇이었는가?
- 수치와 성과는 어떻게 측정했고 재확인할 수 있는가?
- 배포, 테스트, 로그, 모니터링, 장애 대응의 실제 근거는 무엇인가?
- AI가 수행한 부분과 후보자가 판단·검증·수정한 부분은 각각 무엇인가?
- 프로젝트는 현재 동작하고 있으며 최근에는 어떻게 관리했는가?
- 공개하면 안 되는 정보, 설명하기 어려운 주장 또는 숨기고 싶은 한계가 있는가?
- 해당 근거는 이력서, 포트폴리오, README, GitHub와 블로그 중 어디에서 가장 잘 증명되는가?

## 8. 절대 규칙과 기본 휴리스틱의 구분

기밀 보호, 사실성, 설명 가능성, 정확한 개인 기여, 동작 상태의 정직한 공개는 절대 규칙이다.

프로필 사진, 자기소개 약 3줄, 이력서 약 3페이지, 링크 한두 개, 6개월 단위 갱신과 하나의 포트폴리오 프로젝트 집중은 기본 휴리스틱이다. 지원 환경과 실제 경험에 더 적합한 이유가 있으면 변경할 수 있으며, 변경 이유를 설명할 수 있어야 한다.

## 9. 아직 정하지 않은 부분

- 질문에 답하기 전에는 수정 제안을 보류할지, `확인 필요` 제안과 질문을 함께 보여줄지
- 이 규칙을 하나의 skill로 만들지, 작성 agent와 검토 agent로 나눌지
- 이력서와 포트폴리오가 공유할 규칙과 각각의 전용 출력 계약
- 규칙 간 충돌을 평가할 테스트 사례와 합격 기준
