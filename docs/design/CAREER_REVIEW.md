# Career Review 설계 및 파일 단위 구현 계획

상태는 **설계안(P0)**이다. 2026-11-23 로컬 HEAD `0daa742`와 당시 작업 트리를 기준으로 했다. 경험 작성·면접 준비, 워크스페이스 모델과 OpenAPI 일부에는 커밋 전 변경이 있었다. 표에서 ‘신규’로 표시한 파일, API와 데이터 필드는 후속 구현 대상이다.

이력서에는 기존 최종 검토에 한국어 문체와 공고별 근거 평가를 추가한다. 포트폴리오는 같은 작업 공간에 문서 버전과 페이지별 평가를 둔다. 사용자에게는 원문을 보존한 채 근거가 있는 수정안이나 답할 수 있는 질문을 제시한다.

## P1 한국어 문체 교정

문체 후보는 글쓴이가 AI를 사용했다는 증거가 아니다. 규칙은 독해를 방해하거나 사실을 모호하게 하는 표현을 찾는다. 아래 가운데 열은 사진의 교정 방향이며, 오른쪽은 제품에서 적용할 조건과 반례다.

| 원문 후보 | 사진의 교정 방향 | 적용 조건 또는 원문을 유지할 반례 |
|---|---|---|
| 이어 봅니다 | 이어 갑니다 | 시도와 지속을 구별한다. 시험 삼아 연결했다면 지속한 것으로 바꾸지 않는다. |
| ~하지 않고 | ~하는 대신 | 대체 행동인지 확인한다. ‘원본을 저장하지 않고 해시만 저장했다’의 부정은 보존한다. |
| ~하는 구조입니다 | ~입니다 | 군더더기일 때 줄인다. ‘쓰기와 읽기를 분리하는 구조’처럼 구조가 설명 대상이면 유지한다. |
| 판정했습니다 | 정했습니다 | 단순 선택인지 검사 결과 판정인지 확인한다. ‘기준 초과로 불합격 판정했다’는 후자다. |
| 반복되는 ~만 | ~은, ~는 | ‘관리자만 접근한다’처럼 범위를 제한하는 조사는 유지한다. |
| 남는 결과를 | 얻게 될 결과를 | 이미 남은 산출물을 향후 기대 성과로 바꾸지 않는다. |
| 그것이 곧 ~입니다 | 그것으로 ~합니다 | 정의·동일성 설명과 수단·행동을 구별한다. |
| ~이 따라옵니다 | ~의 성과를 낼 수 있습니다 | 실제로 관찰한 결과와 가능한 효과의 확실성을 보존한다. |
| 기록으로 남겼습니다 | 적었습니다 | 단순 서술은 줄인다. 감사 로그·설계 결정 기록처럼 기록물의 종류가 근거이면 보존한다. |
| ~임을 압니다 | ~임을 알 수 있습니다 | 사진 원문은 ‘임을 압니다’다. 본인이 확인한 사실을 일반적 가능성으로 바꾸지 않는다. |
| 이 순서로 갔습니다 | 이 순서로 진행했습니다 | 작업 순서를 서술할 때만 적용한다. 이동 경로나 탐색 경로를 뜻하면 유지한다. |
| 템플릿을 통해 단축 | 템플릿으로 줄임 | 수단·대상·시제를 유지한다. 단축한 대상이나 시간을 새로 넣지 않는다. |
| 데이터에 대한 분석을 수행 | 데이터를 분석 | ‘분석을 수행했습니다’의 주체가 같으면 ‘분석했습니다’로 줄인다. 분석을 지원한 경력은 구별한다. |
| 중요한 의미를 가집니다 | 중요합니다 | 평가만 간결하게 한다. 왜 중요한지 적힌 설명은 남긴다. |
| ~되었습니다, ~보여집니다 | ~했습니다, ~보입니다 | 주체가 명시되어야 능동형으로 바꿀 수 있다. 자동 복구된 시스템을 ‘제가 복구했습니다’로 바꾸지 않는다. |
| 혁신적인·획기적인·탁월한 | 숫자로 설명 | 같은 프로젝트·지표·조건의 근거가 있을 때만 쓴다. 사진 속 ‘3시간 → 40분’은 지원자의 실적이 아니다. |
| 다양한 경험·풍부한 경험 | 경험의 개수와 이름 | 원문에서 확인한 경험만 사용한다. 사례 두 개가 경력 전체의 개수라는 보장은 없다. |
| 또한·나아가·결론적으로 | 빼도 뜻이 통하면 삭제 | 나열·인과·결론의 관계가 흐려지면 유지한다. |
| ~에 기여했습니다 | 내가 한 행동과 결과 숫자 | ‘팀의 응답 시간 개선에 기여했습니다’만 있다면 ‘직접 변경한 부분은 무엇인가요?’라고 묻는다. |
| 문장 가운데 긴 줄표 | 쉼표나 마침표 | 삽입 설명인지 확인한다. 원문 인용, 기술 식별자, 범위 표기는 보존한다. |
| 소제목마다 붙은 이모지 | 삭제 | 장식이 반복되어 읽기 어려울 때 대표 위치 한 곳을 제안한다. 상태 구분에 쓰인 기호는 유지한다. |
| 세 개씩 나열한 형용사 | 가장 중요한 하나 | 같은 의미를 반복할 때 줄인다. 서로 다른 요구조건 세 가지는 보존한다. |

**처리 순서.** 순수 Python 함수가 원문 줄·규칙 ID·후보 범위를 찾는다. 기존 최종 검토가 주변 문맥과 입력 버전에 고정된 근거를 읽어 유지, 축약, 확인 질문 중 하나를 선택한다. 서버는 등록된 규칙과 인용 위치, 수정 대상과 근거의 관계를 검사한다. P1에서 바로 쓸 수정문은 동일 주체·동작·대상·시제를 유지하는 제한된 축약으로 한정한다. 숫자가 문서 어딘가에 존재한다는 검사만으로는 다른 프로젝트의 수치를 옮기는 오류를 잡을 수 없다. 근거가 모호하면 질문을 표시하고, 자연스러운 문장은 결과에서 제외한다.

**비용과 품질.** 프롬프트만 추가하면 수정량은 작지만 후보 누락과 오탐을 재현하기 어렵다. 문체 전용 LLM 단계를 독립시키면 개별 재시도가 가능하지만 호출과 대기 시간이 늘고 기존 가독성 제안과 충돌한다. P1은 기존 호출에 후보를 묶어 보내고, 반복 표현은 대표 위치로 제한한다. 호출 횟수와 별개로 입력 토큰 증가, 안전한 축약의 채택률, 자연스러운 문장의 오탐을 측정한다.

## 계약·화면·저장

**이력서(P1).** 기존 한글 별칭, SuggestionKind와 reviewSources를 유지한다. 출처는 공고·회사 자료·기본 검토 중 어떤 근거를 사용했는지 나타낸다. 아래 필드는 별도의 진단 정보다.

```ts
type CareerDiagnostic = {
  category: "writing-style" | "evidence" | "job-alignment" | "resume-strategy";
  ruleId: string;
  action: "rewrite" | "ask";
};
type SuggestionExtension = { diagnostic?: CareerDiagnostic | null };
type ReviewRecordExtension = { policyVersion?: string | null };
```

Pydantic의 SuggestionDTO에 대응하는 선택 필드를 추가하고, 서버가 실행 시작 시 정책 버전을 고정한다. ask는 필수 example에 ‘[확인 필요: 직접 변경한 부분]’처럼 안전한 값을 담고, 새 카드는 reasonAndSuggestion의 질문을 ‘확인할 내용’으로 표시한다. 과거 기록에서 메타데이터가 없으면 기존 카드로 읽는다. 이력서 시작·결과 API와 재시도 모듈 키는 그대로 쓴다.

`/contexts/:contextId` 화면은 **원문 미리보기 | 전체·내용/근거·문체 필터와 제안 카드**로 구성한다. 안전·기밀과 사실성 문제를 문체보다 먼저 표시한다. 필터를 적용하기 전의 번호와 제안 ID로 원문을 선택한다. 조회 중인 원문 버전이 다르면 그 위에 다른 버전의 강조를 그리지 않는다.

**공고 적합성(P2).** 공고 요구별로 공고 버전과 인용, 연결한 이력서 줄 또는 경험 버전과 인용, 근거 수준(맞음·부분·자료에서 확인되지 않음)을 저장한다. 위치가 있는 개선은 기존 카드에, 원문 전체에 없는 요건은 공고 요약에 표시한다. 임의의 첫 줄에 누락 사항을 연결하지 않는다. 공고가 없으면 공고 기반 결론도 없다. 역할·측정 조건을 확인할 수 없는 성과는 질문으로 남긴다.

**포트폴리오(P3).** 같은 context에 portfolioVersions와 portfolioReviews를 추가한다. 자료 보관함만으로는 평가 대상과 페이지별 이력을 고정하기 어렵고, 기존 ResumeVersion을 모두 범용 문서 모델로 이관하면 과거 제안 복원까지 바뀐다. 별도 버전 컬렉션은 소유권·파일 저장을 공유하면서 이 변경을 국한한다.

| 계약 초안 | 검증과 표시 |
|---|---|
| PortfolioVersion(id, contextId, originalFileId, document) | 원본과 PageDocument를 고정한다. 기존 모델처럼 pageNumber는 1부터 시작한다. |
| PortfolioReview(id, contextId, portfolioVersionId, policyVersion, pages, findings, status, errors) | 페이지마다 텍스트·이미지 평가 상태를 남긴다. 완료 후 문제 없음, 평가 미실시, 실패를 구별한다. |
| PortfolioFinding(ruleId, pageNumber, basis, quote?, bbox?, diagnosis, proposedChange) | text는 해당 버전·페이지의 인용을 검증한다. image는 분석한 페이지 및 정규화 영역을 확인한다. 페이지 전체 문제는 영역 없이 표시할 수 있다. |
| POST /api/contexts/{contextId}/portfolio-versions/{versionId}/reviews → 202 {runId} | 서버가 소유자와 버전을 확인한다. 실행 이벤트·취소 경로는 공유하고 결과·복원은 포트폴리오 계약을 사용한다. |

`/contexts/:contextId/portfolio`는 **버전 선택 → 페이지 미리보기 | 현재 페이지 평가와 수정 방향**을 제공한다. 텍스트로 제목·역할·수치의 근거를 평가한다. 시각적 계층·차트 가독성·이미지와 주장의 일치는 실제 페이지 렌더링이 성공한 경우에만 판단한다. OCR의 PyMuPDF 렌더링을 재사용하며 이미지 실패 시 텍스트 결과는 남긴다. 페이지 수·해상도·요청당 묶음 크기는 대표 PDF의 지연과 비용을 측정한 뒤 정한다.

**영속화와 권한.** P1은 JSON 선택 필드 추가로 처리한다. 엄격한 Pydantic 읽기·가져오기 계약을 먼저 확장하고 새 필드를 기록한다. 정책 버전 없는 기록은 소급 분류하지 않는다. 저장된 정책을 지원하지 않는 재시도는 기존 결과를 보존하고 새 정책의 새 실행으로 안내한다. P3은 구형 snapshot에 누락된 컬렉션을 빈 목록으로 읽고, 파일 참조 수거·백업·가져오기에서 포트폴리오 원본도 추적한다. 저장 시 owner·context·문서 버전·활성 run이 모두 일치해야 한다. 사용자별 Gateway 인증, 도구 없는 최종 검토, 원본 파일 접근 경계를 재사용한다.

## P3·P4 구현 기준

포트폴리오 화면에서 PDF 버전과 페이지를 고른다. 한 페이지를 평가하거나 남은 페이지를 순서대로 평가할 수 있다. PDF는 25 MB, 30페이지 이하다. 각 요청이 완료될 때마다 버전과 페이지에 평가 이력을 추가한다. 포트폴리오는 페이지 요청의 진행 표시와 연결 취소를 사용하고, 이력서의 SSE는 이력서 검토에서 계속 사용한다. 페이지 이미지 분석이 실패하면 텍스트 평가를 시도한다. 텍스트 레이어 없는 PDF는 이미지 평가를 지원하며, 해당 페이지의 텍스트 인용이 필요한 문서 간 비교에는 참여하지 않는다.

문서 간 비교는 페이지 평가와 같은 호출에서 진행한다. 검토 시점의 이력서와 선택한 경험을 사용한다. 선택이 비어 있으면 분량 한도 안에서 본문이 있는 경험을 사용한다. 결과에 당시 출처 종류·버전·원문 인용을 남긴다. 모델이 제시한 값이 양쪽 원문 인용에 있고 각 인용을 해당 문서에서 찾을 수 있을 때만 차이를 보여준다. 동일 프로젝트와 비교 조건인지는 모델이 판단하므로 결과를 ‘확인’ 대상으로 표시한다.

이력서와 포트폴리오는 사실성, 개인과 팀의 기여 구분, 수치 근거, 기밀 보호와 자연스러운 문체를 공통 검토 기준으로 사용한다. 포트폴리오는 페이지 제목, 읽는 순서, 실제 이미지의 대비와 차트 가독성을 추가로 평가한다. 제목·본문·캡션을 원문 인용으로 안전하게 고칠 수 있으면 평가의 선택 필드 `replacementText`에 개선 문장을 저장한다. 근거가 부족하거나 레이아웃만 바꿀 때는 확인 사항과 수정 방향을 표시한다. 이전 평가 기록은 기존 수정 방향으로 열리며, 개선 문장을 받으려면 페이지를 다시 평가한다.
