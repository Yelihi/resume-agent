# 용량 확장·자료 삭제·원본 복구

2026-09-26 코드와 운영 설정 확인 기준. 아래 확장 절차와 개선 항목은 계획이며 실제 디스크 교체·데이터 삭제·복원은 실행하지 않았다. 현재 서비스 운영은 [운영 설명서](../../deploy/OPERATIONS_GUIDE.md)를 따른다.

## 먼저 어느 디스크가 부족한지 구분한다

| 디스크 | 저장 대상 | 확인 당시 여유 |
| --- | --- | --- |
| 외장 SSD `/Volumes/Storage2TB` | 운영 DB·원본, 코드 release, 모델 캐시, 백업용 임시 사본 | 약 1.6TiB |
| Mac 내장 디스크 | macOS·다른 사용자 자료와 restic 암호화 백업 | 약 23GiB |

운영 데이터와 백업은 다른 물리 디스크에 있다. 현재는 내장 백업 공간을 먼저 관리할 필요가 있다. 백업 스크립트는 외장 SSD의 staging에 DB와 참조 중인 원본 파일의 일관된 사본을 만든 다음 restic에 저장하므로, **운영 데이터 크기 외에 임시 사본을 만들 여유도 필요하다.** restic의 중복 제거가 staging 사본까지 없애 주지는 않는다.

## 백업에는 파일 내용도 들어간다

백업 대상은 `resume.sqlite3`와 DB의 `files` 테이블에 등록된 **파일의 실제 바이트**, 그리고 무결성 검사용 `manifest.json`이다. 파일 경로 목록만 저장하는 방식이 아니다. 외장 SSD의 `backup-staging`에 일관된 임시 사본을 만들고 검증한 뒤, 내장 디스크의 `~/Library/Application Support/resume-agent-backup/restic`에 암호화하여 저장한다. 정상 종료하면 임시 사본은 정리한다. 모델 캐시와 별도 설정·비밀 키 폴더는 이 백업에 포함하지 않는다.

최신 사본 하나만 남기지 않고 일별 7개·주별 4개·월별 3개 보존 규칙을 적용한다. 실제 데이터는 restic이 중복 제거하므로 스냅샷 개수만큼 전체 파일을 반복 저장하지 않는다. 예를 들어 변경 없는 원본 1GB를 여러 번 백업해도 원본 내용이 매번 1GB씩 추가되지는 않는다. 새로운 파일·달라진 내용·메타데이터는 공간을 추가로 사용하며, PDF·이미지는 압축 효과가 작을 수 있다. [restic 백업·중복 제거](https://restic.readthedocs.io/en/stable/040_backup.html).

최신 사본만 남기면 손상된 상태가 백업된 뒤 정상 과거본을 잃을 수 있다. 현재 코드는 파일 누락·크기 불일치를 잡지만 **크기가 같은 내용 손상은 업로드 당시 해시와 비교하지 않는다.** 백업 때 만든 해시는 그 백업 이후의 무결성을 검증하며, 이미 손상된 원본이 정상이라는 보장은 아니다.

## 디스크 손상에 대비하는 방법

원본이 손상돼도 해당 파일의 정상 내용이 남은 과거 백업이 있으면 복원할 수 있다. 운영·백업 디스크가 함께 손실되거나 백업 전 파일이 사라진 경우는 별도 대비가 필요하다. 일반적인 보호 방법은 다음과 같다.

- 운영 원본과 백업을 분리하고 여러 시점을 보관한다. 실시간 복제만으로는 삭제·손상이 전파되는 문제를 막지 못한다.
- 장치·장소·접근 권한이 다른 추가 사본과 오프라인 또는 변경·삭제가 제한된 백업으로 동시 손실 범위를 줄인다.
- 정기 무결성 검사, 별도 폴더에서의 시험 복원, 백업 실패 알림으로 실제 복구 가능성을 확인한다.

현재는 외장 운영 SSD와 내장 백업 디스크까지 분리되어 있다. 장치 밖 사본·독립된 복구용 키 보관·정기 복원 검증·실패 알림은 추가할 과제다. RAM 증설은 데이터 보존 대책이 아니며 백업용 서버가 반드시 필요한 것도 아니다. 현재 백업 코드는 로컬 경로만 허용하므로 원격 백업은 별도 구현·검증이 필요하다. [CISA 백업 권고](https://www.cisa.gov/stopransomware/ransomware-guide).

## model-cache의 역할

2026-09-27 확인 시 `model-cache/paddlex`에는 글자 영역 탐지 모델 `PP-OCRv5_mobile_det`와 한국어 문자 인식 모델 `korean_PP-OCRv5_mobile_rec`가 약 18MiB, `huggingface`에는 모델 다운로드 관련 메타데이터·로그가 약 64KiB, `uv`에는 Python 설치 캐시가 약 873MiB 있었다. 시작 스크립트는 `paddle`, `.cache` 경로도 지정하지만 해당 폴더는 당시 없었다.

이는 모델·패키지의 재다운로드를 줄이는 **디스크 캐시**다. `_paddle_pipeline()`은 별도로 `lru_cache(maxsize=1)`를 사용하여 같은 서버 프로세스에서 OCR 모델 객체를 재사용한다. 서버를 재시작하면 메모리 객체는 다시 초기화하지만 디스크의 모델 파일은 남는다.

문서별 OCR 결과·AI 검토 결과를 이 폴더에 캐싱하지 않는다. 저장 완료된 문서의 추출 내용은 DB에 보관해 다시 볼 때 활용하지만, 동일 파일 재업로드 시 추출 요청은 다시 발생한다. 반복 변환이 실제 병목으로 확인되면 사용자 범위·파일 내용 해시·추출기 버전을 기준으로 결과 재사용을 검토한다. 현재 개선에서는 새 캐시를 추가하거나 기존 캐시를 삭제하지 않았다.

## 확장 순서

1. **사용량 파악:** 운영 원본, 백업, 모델 캐시, 과거 release와 Mac의 다른 자료를 구분한다. 현재 버전·복구용 사본의 필요성을 확인하기 전 일괄 삭제하지 않는다. 용량 경보·사용자별 할당량·오래된 release 자동 정리는 아직 없다.
2. **내장 백업 공간 부족:** 별도의 백업용 외장 디스크로 기존 restic 저장소를 옮기는 방식이 먼저다. 기존 암호와 스냅샷을 유지한 채 백업 실행을 멈추고 복사·무결성·시험 복원을 검증한 뒤 `RESTIC_REPOSITORY`, 권한, 자동 실행 시 마운트를 확인한다. 운영 SSD와 백업 SSD를 분리한다. 현재 스크립트에는 원격 restic 저장소를 거부하는 제약이 있다.
3. **운영 SSD 공간 부족:** 더 큰 SSD로 운영 데이터를 이관한다. 서버 쓰기·배포·예약 백업을 멈춘 상태에서 DB와 파일을 함께 복사하고 검증한 뒤 전환한다. 운영 DB가 열린 상태에서 SQLite 파일 하나만 복사하지 않는다. 디스크 UUID·표시 파일·경로·권한 검사, `RESUME_STORAGE_ROOT`, `RESUME_DATA_DIR`, 모델 캐시와 staging, 서비스 실행 앱과 배포 경로도 함께 확인해야 한다. 현재 코드에는 고정된 운영 경로도 있어 설정 한 줄 변경만으로 이관 완료를 보장하지 않는다.
4. **여러 서버나 대규모 파일 저장이 필요해질 때:** 원본 파일을 객체 저장소로 분리하는 설계를 검토한다. 현재 파일 API는 `data/files`의 로컬 파일과 `FileResponse`를 사용하므로 S3 호환 저장소 등을 연결하려면 업로드·다운로드·소유권·삭제·백업 구현을 함께 변경해야 한다. 현재 SQLite를 NAS 공유 경로로 단순 이동하는 방식은 확장 절차로 삼지 않는다.

확장 시에도 서비스 주소와 파일 ID를 유지하면 사용자 화면의 변경을 줄일 수 있다. 우선 현재 로컬 디스크 구조에서 확장하고, 실제 사용량이 필요성을 보여줄 때 저장소를 분리한다.

## 앱에서 삭제하면 어떻게 되나

현재 자료 보관함의 삭제와 작업 공간 삭제는 구현되어 있다. 파일 참조를 제거한 뒤 어디에서도 참조하지 않는 파일의 DB 정보와 SSD 원본을 정리한다. 사용자 화면에서 가능한 삭제 범위는 다음과 같다.

| 작업 | 실제 효과 |
| --- | --- |
| 작업 공간에서 자료 연결 해제 | 연결만 제거. 보관함 자료와 원본 유지 |
| 자료 보관함에서 삭제 | 목록에서 제거하고 연결 해제. 과거 검토·진행 중 검토·경험 작성본에서 필요한 버전은 유지 |
| 작업 공간 삭제 | 그 작업 공간의 이력서 버전·검토·피드백·경험 작성본 삭제. 공용 보관함 자료는 유지 |
| 마지막 파일 참조가 제거됨 | DB의 해당 파일 정보와 SSD의 원본 파일 삭제 |

따라서 **화면에서 삭제했다고 항상 즉시 파일 용량이 줄어드는 것은 아니다.** 과거 검토를 재현하기 위해 참조 중인 원본은 남는다. 백업에 들어 있는 사본도 별도로 남는다. 현재 백업 보관 정책은 일별 7개·주별 4개·월별 3개이며 정책 간 중복될 수 있다. 더 이상 보관할 스냅샷이 참조하지 않는 데이터가 prune으로 정리될 때 백업 공간이 회수된다. [restic 보관·정리 설명](https://restic.readthedocs.io/en/stable/060_forget.html).

아직 **경험 보관함 원본 기록 자체의 삭제**, 개별 과거 이력서 버전 삭제, 사용자별 사용량·할당량, 휴지통·복원 UI, 주기적인 고아 파일 정리는 구현되지 않았다. 경험 작성본 삭제는 경험 원본 기록 삭제와 다르다. 삭제 기능 전체가 완성되었다고 보지는 않는다. 이 기능을 추가할 때는 참조 관계와 과거 검토 보존 정책을 먼저 정해야 한다.

## SSD에서 원본을 직접 지우면

`data/files/<파일 ID>`를 Finder나 터미널에서 직접 지우면 DB 참조는 남는다. 목록·추출된 텍스트·과거 검토는 남아 보일 수 있지만 원본 미리보기·다운로드는 `404 원본 파일을 찾을 수 없습니다`로 실패한다. 서버 전체가 반드시 바로 중지되는 것은 아니다.

다음 백업은 DB가 참조하는 파일을 찾지 못해 실패하며 `backup-status.json`에 오류를 기록한다. 현재 백업 코드에서는 이 실패 시 새 정상 스냅샷 생성과 보관 정리 단계로 진행하지 않는다. 배포 전 백업도 실패하므로 정상적인 백엔드 배포가 막힌다. 자동 파일 복구나 별도 장애 알림은 없다.

복구는 다음 순서로 판단한다.

1. 쓰기와 배포·예약 작업을 잠시 중단하고 남은 DB·파일 상태를 보존한다. 망가진 상태를 정상 백업으로 간주하지 않는다.
2. 삭제된 파일이 실제 들어 있는 기존 성공 스냅샷을 찾는다. `latest`가 반드시 그 파일을 포함하는 것은 아니다.
3. **빈 별도 폴더에** 복원하고 manifest·해시·DB 참조와 파일 크기를 검증한다. [restic 복원 설명](https://restic.readthedocs.io/en/stable/050_restore.html).
4. DB가 온전하고 같은 파일 ID의 원본만 없어진 경우에는 검증한 원본을 기존 ID·소유권·권한으로 되돌린다. 관련 없는 최신 DB를 과거 버전으로 덮어쓰지 않는다. DB도 손상됐다면 검증된 같은 시점의 DB·파일 묶음으로 복구해야 한다.
5. 원본 다운로드·health·새 백업을 확인한 뒤 예약 작업과 배포를 재개한다.

파일이 백업되기 전에 삭제됐거나 포함된 스냅샷이 이미 정리됐다면 백업으로 복구할 수 없다. 보유 원본으로 다시 등록하거나 별도 복구 작업이 필요하다. 단순 재업로드는 새 파일 ID를 만들므로 기존 참조를 자동 복구하지 않는다. 평소 삭제는 앱의 삭제 기능을 사용한다.
